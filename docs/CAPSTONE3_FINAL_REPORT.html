1. Project and Problem Description

Kistie Store is a publicly deployed women’s apparel and accessories e‑commerce web application oriented to a Kampala‑based fulfillment model with worldwide online shoppers. Small fashion retailers increasingly require a storefront that blends discoverability on the web, straightforward cart behavior, multilingual‑friendly tooling, security around staff operations, and a path toward mobile‑money‑style fulfillment without demanding that every shopper install a proprietary app.

The problem addressed by this Capstone project is operational and customer‑experience fragmentation: boutiques often mix informal channels (messaging apps, spreadsheets, ad‑hoc payment confirmation) with limited web presence. Customers need a consistent place to browse inventory with filters, clear sizing and payment guidance, and a single cart and checkout flow; operators need limited but effective staff views (dashboard, audit trail, optional Django admin) and APIs that can support automation or future mobile clients. The deliverable aligns with Agile delivery practice: iterative enhancement of storefront, API, staffing tools, CI testing, and optional AI assistants on the Shop experience.

The production stack employs Django 5 for server‑rendered pages and REST endpoints (Django REST Framework), SQLite for local development and PostgreSQL where configured for cloud hosting, Bootstrap for responsive layout, and GitHub Actions for continuous integration testing. Experimental React (Vite) client code complements the codebase for SPA‑style prototyping and tooling; the authoritative customer storefront in production remains Django‑templated routes such as /shop/, /cart/, and /checkout/.

2. Requirements Expressed as User Stories

Below, requirements are enumerated in agile user‑story format: As a [role], I want [goal], so that [benefit]. Acceptance summaries reference implemented routes or artifacts in the codebase.

ID User story Acceptance summary
US‑01 As a shopper, I want the home entry to take me directly to the shop, so that I can start browsing without extra navigation. / redirects to /shop/; covered by automated tests.
US‑02 As a shopper, I want to filter products (for example by category and price) and open a quick view, so that I can decide what to buy efficiently. Implemented in core/shop.html with server‑side filters and modal quick view.
US‑03 As a shopper, I want a cart and checkout with currency context, so that I can submit an order with clear totals. /cart/, /checkout/; checkout guards empty carts; tests validate add‑to‑cart, stock limits, and order creation flows.
US‑04 As a shopper, I want to create an account and sign in, so that my basket can merge reliably and I can see order history. /signup/, /login/, /account/orders/; Django auth and session semantics.
US‑05 As a shopper, I want sizing help and optionally an assistant for product questions, so that EU sizing feels less intimidating. Quick‑view sizing via POST /api/size-recommend/; storefront chat bubble uses POST /api/chat/; degrades gracefully if AI keys absent.
US‑06 As a shopper, I want to read about the brand, contact the business, and see terms, so that I understand policies and trust the store. /about/, /contact/ (persists inquiries, email when SMTP configured), /terms/.
US‑07 As an operator / staff member, I want a staff sign‑in and dashboard with permission checks, so that only authorized users see internal snapshots. /staff/login/, /staff/dashboard/; dashboard tests cover anonymous redirect, permission denial, and allowed roles.
US‑08 As a superuser, I want an audit log and tightly gated Django admin, so that sensitive configuration is not exposed to regular shoppers. /staff/audit-log/; admin allowed only with superuser and feature flags; middleware tests exercise admin access rules.
US‑09 As a developer or integrator, I want read‑mostly JSON for products and categories with staff‑only writes, so that future clients can consume data safely. DRF under /api/inventory/; permission tests for anonymous, shopper, and staff create operations.
US‑10 As a DevOps stakeholder, I want health checks and CI on every mainline change, so that regressions are caught early. /health/ JSON; GitHub Actions workflow runs python manage.py test on Python 3.12.

4. Documentation of Tests Conducted

4.1 Automated backend (Django) tests

The project ships an automated suite executed with python manage.py test from the backend/ directory (36 tests at time of report authoring). Tests are distributed across application modules and exercise HTTP behavior, permissions, redirects, inventory validation rules, cart limits, checkout with order creation, and admin/staff‑portal access control.

Representative inventory (from core/tests.py): health JSON (test_health_json); shop template render; home and legacy URL redirects preserving query strings; signup flow; anonymous and role‑scoped staff dashboard access; admin superuser‑only middleware behavior.

cart/tests.py: anonymous cart load; adding items; rejection of oversize quantities vs stock and invalid sizes; checkout clearing cart after order creation; housekeeping of stale guest carts.

inventory/tests.py: DRF GET endpoints for products and categories; anonymous and shopper prohibition on destructive category mutations; partial product stock updates; enforcement of acceptable EU‑size payloads.

Layer Command / trigger Outcome criterion
Local developer cd backend && python manage.py test Exit code 0; all tests passing.
Continuous integration GitHub Actions workflow ci.yml on push/PR to main/master Ubuntu runner, Python 3.12, installs requirements.txt, runs same Django suite.

4.2 End‑to‑end / smoke testing (Playwright)

Under frontend/tests/smoke.spec.js, a Playwright smoke pack validates production‑adjacent UX without seeded credentials:

  1. Health endpoint returns JSON with status: ok and service identifier.
  2. Root path issues HTTP 302 redirect whose Location ends with /shop/.
  3. Rendered shop page exposes currency selector (#inventoryCurrency) and coherent title metadata.
  4. Anonymous cart route loads with expected heading copy.
  5. Checkout with empty basket redirects shopper back to cart.
  6. Staff login page reachable with instructional heading.

Run prerequisite: Django listening on configurable PLAYWRIGHT_BASE_URL, default http://127.0.0.1:8000; install Node dependencies inside frontend/ and execute npm run smoke.

4.3 Manual / exploratory verification

Recommended exploratory passes before demo day: multilingual chat prompts (English and sample Luganda phrasing); contact form SMTP vs console backend; Pesapal initiation URL pointing to local or deployed Node payments shim; staff permission matrix for dashboard vs shopper accounts; responsiveness at mobile breakpoints for shop grid and navbar collapse.

Appendix B — Major Local Development Issues Encountered and Resolutions

During final integration and tooling work, several recurring obstacles affected reliable local runs (manage.py runserver plus optional Vite on Windows). Below are the major items only—not an exhaustive defect log. Automated regression consisted of running the Django suite (36 passing tests via python manage.py test), continuous integration parity on GitHub Actions, and optional Playwright smoke checks documented in Section 4.2.

Major issue Symptoms / evidence Steps taken to correct
Cross‑origin calls from the React dev server (:5173) to the Django API (:8000) in development Inconsistent SPA loads or cart/session behavior; intermittent browser blocks or unpredictable credentialed fetch results when the browser treated the two ports as different origins. Configure Vite to proxy all /api paths to Django (not only inventory). Point the SPA at same‑origin relative URLs such as /api/inventory in development so requests flow through Vite. Harden optional dev‑only middleware: Access-Control-Allow-Credentials, CSRF token header allowance, and CSRF_TRUSTED_ORIGINS including http://localhost:5173 and http://127.0.0.1:5173.
Starting the frontend before the Django process was accepting connections Early browser opens showed empty data, failed scripts, or “network errors” until a manual refresh after the backend came up. Provide scripts/start-local.ps1: start Django first, poll GET http://127.0.0.1:8000/health/?format=json until HTTP 200, then launch npm run dev; document the order in README and README.txt.
Local environment pointing at a remote database via DATABASE_URL Delayed page loads, connection errors, or failed migrations when the cloud instance slept, quotas applied, or the network blocked access—often mistaken for “broken app.” Document stripping or commenting DATABASE_URL during pure local SQLite work; clarified in backend/.env.example that SQLite is default when omitted; instruct developers to recreate .env consciously per environment.
Windows PowerShell command compatibility Chains using bash-style && failed on shells where that operator was unsupported or parsed incorrectly, preventing one‑line automation from starting servers. Standardized examples on Set-Location (cd) plus semicolon separation or dedicated .ps1 helpers; avoids fragile copy‑paste snippets in mixed PowerShell versions.

Verification after fixes: From the project root after installing Python dependencies: open backend/, run python manage.py test until all tests succeed; optionally install Node packages under frontend/ and run npm run smoke while Django listens on http://127.0.0.1:8000. CI on main/master repeats the Django suite automatically.
